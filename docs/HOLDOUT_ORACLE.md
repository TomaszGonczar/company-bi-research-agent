# Component holdout oracle

This is the future public toolkit format for expected component results. It does not replace, reinterpret, or rewrite the separately frozen Astra component oracle; Astra's existing shape remains deliberately unchanged. This document defines no corpus and its examples are neutral.

`company_bi.holdout_oracle.HoldoutOracle` is a validation-only Pydantic model. Its JSON Schema is available from `HoldoutOracle.model_json_schema()`. The document has a `cases` array. Each case has a unique nonempty `case_id` (IDs are preserved exactly, not trimmed or normalized), `classification`, a canonical supported `target` path, and a discriminated `expected` object. Classifications retain the five strict-case values: `SUPPORTED_CONTRACT_POSITIVE`, `OUT_OF_CONTRACT_TRUE`, `UNSAFE_NEGATIVE`, `IDENTITY_INVALID`, and `PROVENANCE_INVALID`. The final two values are model-boundary controls; the first three are semantic populations.

- `{ "kind": "profile", "state": ..., "value": ... }` checks a final fact profile. `state` and `value` are required, including when expected `value` is null.
- `{ "kind": "reject", "stage": "model" | "run" }` means an explicitly observed rejection at exactly that boundary. Rejection is never inferred from missing, crashed, or malformed output.

Supported target spellings are `business_description`, `products_services`, `industries`, `markets`, `employees`, `financials.N`, `recent_developments.N`, and `identity.legal_name`, `identity.krs`, `identity.regon`, `identity.registered_city`, `identity.registered_address`, `identity.website`. Indexed paths use canonical nonnegative decimal indices (no leading zero except `0`). Resolve a target against a concrete raw run or serialized profile with `company_bi.strict_cases.resolve_fact_path(document, target)`; it rejects nonexistent elements and non-fact/list targets. Oracle validation separately checks allowed path syntax and component-family compatibility.

Profile expectations may add `reason_nonempty`, `evidence_source_ids`, and applicable context: financial `period`, `currency`, `unit`, `scope`, `group_name`; employee `as_of`; event `published_on` and `occurred_on`. Omitted optional components are unassessed. Explicit `null` for a nullable component asserts it is cleared/absent, including optional fields nested under a supported parent (for example `occurred_on: null` or financial `group_name: null`). `evidence_source_ids` must be omitted or a list (null is invalid); expected IDs must be unique and compare as an exact set independent of order. Observed evidence may cite a source ID more than once; repeated citations do not change the compared set, but malformed IDs fail. Reason checks only whether trimmed text is nonempty. Opaque values and labels compare exactly, type-sensitively (for example JSON boolean `true` differs from number `1`), with no normalization. Financial expected `value` is a decimal string or null; serialized observed amounts must also be decimal strings, never floats. Amounts compare by exact Decimal numeric equality (so `\"1.00\"` equals `\"1.0\"`), never via binary float, rounding, tolerance, or formatting normalization. Decimal strings must be finite.

## Scoring contract

Repository-only deterministic scoring lives in `company_bi.holdout_scoring`, outside restricted public toolkit packaging. `score_case` consumes exactly one explicit observation: the complete serialized `profile`, an explicit `rejection_stage`, or `output_missing=True`. It resolves the case's target path against that profile itself; callers cannot supply a different fact, and an emitted profile missing the target is an executed failure. `score_oracle` accepts case-ID-keyed observations and rejects missing or extra IDs. It does not run or import semantic parsers, evidence collection, assertions, verification, or evaluation.

For profile outcomes, scoring reports independent component failures (`state`, `value`, reason, evidence IDs, and any supplied context/date checks). A supported state never masks a wrong value. A successful output cannot satisfy a reject expectation. An explicitly observed `run` rejection satisfies only a matching semantic reject expectation; a `run` rejection where a profile was expected is an executed semantic failure. A model-stage rejection of a semantic case is `unexercised` with no semantic pass/fail result. Missing/crashed output is `unassessed` with an `output_missing` failure, never rejection or PASS. `IDENTITY_INVALID` and `PROVENANCE_INVALID` are boundary controls with semantic execution `not_applicable`; they may expect a profile component result or a rejection at `model` or `run`, and score against that exact expectation. Missing output fails a boundary control.

Before any external execution, report separate denominators/populations for each semantic classification (`SUPPORTED_CONTRACT_POSITIVE`, `OUT_OF_CONTRACT_TRUE`, `UNSAFE_NEGATIVE`). The release-positive denominator includes **all** predeclared `SUPPORTED_CONTRACT_POSITIVE` cases, including model-rejected and missing-output cases; those cases remain in the denominator and count as not passing. Separately report semantic execution (profiles or observed run rejections), model rejections (`unexercised`), and missing outputs (`unassessed`) within each classification. Report `IDENTITY_INVALID` and `PROVENANCE_INVALID` boundary-control denominators and results separately. Report component results against their applicable assessed denominators; omitted components are not failures and are not in that component's denominator. Do not combine boundary controls, the three semantic classifications, unexercised cases, missing outputs, and semantic executions into one accuracy figure. High-level publish/abstain/reject labels alone are not an adequate component oracle.
